# `chaos-rabbitmq.mjs` 讲解

## 作用概览

该脚本验证 RabbitMQ 中断时跨节点消息不会静默消失：消息可能仍在线到达，也可能由发送节点降级写入离线库。

## 按学习顺序讲解

- `trackedClient(port)`：创建并登记客户端供最终清理。
- 场景先在两个节点注册登录用户，再打印 `READY_FOR_RABBITMQ_STOP`；外层 Shell 看到该标记后暂停 broker。
- 中断窗口后发送跨节点消息并等待发送方 ACK。
- 先短时观察在线收件；若未到，则注销/重连接收者并在登录离线列表中寻找同一 ID。
- 断言在线或离线至少一种路径成立，并输出实际路径。
- `finally` 清理客户端。

## 函数详细说明

### `trackedClient(port)`

创建带本场景超时的公共测试客户端，成功后加入 Set 并返回。故障注入期间任何等待都可能抛错，Set 让 finally 能覆盖发送者、原接收者和重连后的接收者。

### 场景初始化

发送者连接节点 1，接收者连接节点 2，分别注册唯一测试账号并登录。只有两个端口背后是不同服务节点时，在线消息才需要 RabbitMQ；若端口相同，测试会退化成本地投递，无法验证 MQ 故障降级。

### 故障同步点

脚本打印 `READY_FOR_RABBITMQ_STOP wait_ms=...`，外层 Shell 监控到文本后暂停 broker。随后 delay 为停止操作和服务端感知连接失败留出窗口。脚本本身不执行 Docker/系统服务命令，使测试逻辑与具体部署方式解耦。

固定等待无法精确证明 broker 已停止，外层应在执行暂停后检查容器/端口状态。输出标记是人工或编排脚本与 Node 场景之间的协议。

### 故障窗口消息与 ACK

发送者构造唯一 `message_id` 的跨节点单聊并等待对应 ACK。由于停机时刻和已建立 MQ 通道存在竞态，ACK 可能表示消息已赶在故障前发布，也可能表示服务端检测发布失败后成功写入离线表。脚本保留 `ack_state` 到报告，不预先假定唯一投递路径。

### 在线观察与离线兜底验证

先给原在线接收者 3 秒观察窗口，若收到同 ID 消息就记录 onlineDelivery。只有明确的 message timeout 被视为“未在线到达”；其他错误继续抛出，避免把连接解析错误误判为正常降级。

未在线收到时，接收者注销并重连登录，解析 `offlinemsg` 查找同一 ID。最终断言 online 或 offline 至少一个存在，证明消息没有静默消失。更严格的测试还应断言两条路径不会同时产生两份，并在 RabbitMQ 恢复后检查积压/重投行为。

### 结果与 `finally`

结构化输出 ACK 状态、实际路径和消息 ID，便于故障报告记录。finally 关闭 Set 中所有连接；原接收者重连前会从 Set 删除，新的客户端重新加入，因此清理对象始终准确。

## 面试重点

重要性高。可能问题：为什么允许两种结果？停止与发布存在竞态，已进入 broker/目标连接的消息可能在线完成，否则应走持久化兜底；ACK 状态和最终路径需要结合解释。
