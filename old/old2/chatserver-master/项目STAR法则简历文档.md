# 项目 STAR 法则简历文档（超详细版）

> 用途：直接用于简历项目描述、面试自我介绍、项目深挖问答。

---

## 一、项目背景（S - Situation）

我基于 Muduo 实现了一个分布式聊天系统。最初版本具备基础聊天能力，但在实际工程维度存在明显短板：
- TCP 粘包拆包导致消息解析风险；
- 消息发送缺少完整可靠性闭环；
- 多节点下重复消息与跨服稳定性不足；
- 静默连接下链路状态不可感知；
- 用户密码明文存储存在高安全风险；
- 项目文档分散，面试表达不够结构化。

---

## 二、任务目标（T - Task）

在不推翻原架构的前提下，完成“高价值、低侵入”的工程化升级：
1. 提升通信稳定性（协议层）；
2. 建立消息可靠性链路（ACK/重试/去重）；
3. 提升多节点通信能力（跨服总线升级）；
4. 改善用户体验（消息按序、连接活性）；
5. 补齐安全基线（密码哈希存储）；
6. 形成可复盘、可面试表达的文档体系。

---

## 三、核心行动（A - Action）

## A1. 协议与网络层改造
- 设计并落地帧协议：`[4字节长度头 + payload]`；
- 客户端发送/接收统一按帧处理；
- 服务端入口从“按 TCP 包”转为“按完整业务帧”处理。

价值：彻底解决粘包拆包导致的 JSON 边界错乱问题。

## A2. 消息可靠性闭环
- 实现客户端 `pending_map`；
- 服务端返回 `MSG_ACK`（`message_id + ack_state`）；
- 客户端实现后台超时重试线程（超时重发，最大次数上限）。

价值：把“发出去就算成功”升级为“有确认才算到达服务端”。

## A3. 去重与幂等控制
- 服务端接入 Redis 原子去重：`SET key 1 EX ttl NX`；
- Redis 失败时自动降级本地 LRU+TTL 去重。

价值：在多实例场景下共享去重状态，避免重复处理；故障时不失效。

## A4. 消息顺序优化
- 识别并修复“全局序号跨会话打洞”问题；
- 单聊改为按 `toid` 维护序号；
- 群聊改为按 `groupid` 维护序号；
- 接收端按会话桶做缓冲重排与连续冲刷。

价值：显著提升消息展示顺序稳定性，避免卡顿与乱序感。

## A5. message_id 升级（Snowflake）
- 将 `message_id` 升级为 64 位雪花 ID；
- 保持 ACK/重试/去重链路兼容。

价值：增强分布式唯一性与可追踪性。

## A6. 连接活性（应用层心跳）
- 客户端周期发送 `HEARTBEAT_MSG`；
- 服务端即时回 `HEARTBEAT_MSG_ACK`；
- 客户端按 ACK 状态识别链路异常。

价值：让静默连接具备可探测性，缩短异常发现时间。

## A7. 跨节点通信升级（Kafka 方案A）
- 将跨服转发由 Redis Pub/Sub 升级为 Kafka；
- producer 配置 `acks=all` 与重试参数；
- 采用“每实例独立组广播消费 + 本地在线过滤”策略。

价值：显著提升跨节点消息投递可靠性，且改造成本可控。

## A8. 安全改造（bcrypt）
- 注册改为 bcrypt 哈希入库（随机盐 + cost）；
- 登录改为 bcrypt 校验；
- 历史明文账号登录成功后自动平滑迁移。

价值：消除明文密码存储风险，符合通用安全基线。

## A9. 质量修复（本轮扫描新增）
- 修复登录分支“悬挂 if”可维护性风险；
- 修复客户端重试日志锁外读取共享 map 的并发风险。

价值：体现对工程细节和稳定性的持续治理能力。

## 六、面试高频追问与回答要点

### Q1：为什么不直接上“恰好一次”语义？
A：工程上优先落地 at-least-once + 幂等去重，复杂度与收益更平衡；恰好一次成本高且链路要求更严格。

### Q2：Kafka 方案A为什么不是最终方案？
A：它是“最小改造优先”的阶段方案，先解决可靠性，再迭代精确路由降低广播开销。

### Q3：为什么要在客户端做重试，不在服务端做？
A：发送方最清楚业务请求是否完成；客户端重试对现有服务端侵入小，落地速度快。

### Q4：bcrypt 为什么适合密码场景？
A：不可逆、带随机盐、可调成本，对抗离线爆破能力强，且行业实践成熟。

### Q5：你做过最有价值的“非功能性优化”是什么？
A：可靠性闭环（ACK+重试+去重）和并发安全修复（锁外共享读问题），因为这类问题最影响线上稳定性。
