# 应用层心跳机制问题

## 所解决的问题

本次解决的是：**长连接在异常网络下“假存活”时，客户端无法及时感知连接可用性**的问题。

项目已经具备：
- TCP 长连接；
- 业务消息 ACK（`MSG_ACK`）；
- 业务消息超时重试。

但这些机制主要作用在“有业务消息在传输时”。如果用户长时间无操作，连接即使已经半开（half-open）或被中间网络设备清理，客户端也可能一直误以为在线。

---

## 为什么需要应用层心跳机制

### 1. TCP 连接“已建立”不等于“应用链路可用”
- TCP 在某些异常场景中不会立即上报断开；
- NAT/防火墙可能提前回收空闲连接映射；
- 设备休眠、网络切换后，链路可能已失效但本地 socket 暂时没有错误。

### 2. 业务 ACK 不能覆盖“长时间静默”的窗口
- ACK 只有在你发送业务消息时才会触发；
- 用户如果 5 分钟没发消息，5 分钟内连接状态不可知。

### 3. 心跳能把“被动发现”变成“主动探测”
- 定时发送轻量心跳包；
- 定时等待心跳 ACK；
- 可以更快发现连接异常，提升可观测性与用户体验。

---

## 如果没有心跳机制会产生什么问题

1. **半开连接长期存在**：客户端显示在线，但实际消息不可达。
2. **故障发现滞后**：只有下一次发业务消息才报错。
3. **用户体验差**：表现为“发出去没反应”或“很久后才失败”。
4. **状态判断不可靠**：无法区分“静默正常”与“静默异常”。

---

## 具体实现方案

### 协议层新增两类消息
- `HEARTBEAT_MSG`：客户端 -> 服务端（心跳请求）
- `HEARTBEAT_MSG_ACK`：服务端 -> 客户端（心跳应答）

### 客户端侧
- 新增心跳线程，每 `10s` 发送一次心跳；
- 发送前检查上一轮 ACK 是否到达；未到达则打印告警；
- 收到 `HEARTBEAT_MSG_ACK` 后标记为已确认。

### 服务端侧
- 在消息处理表中注册 `HEARTBEAT_MSG` 处理器；
- 收到心跳后立即返回 `HEARTBEAT_MSG_ACK`；
- 可回显客户端 `ts` 作为调试依据（`echo_ts`）。

### 3) 服务端心跳处理函数

```cpp
void ChatService::heartbeat(const TcpConnectionPtr &conn, json &js, Timestamp time)
{
    json ack;
    ack["msgid"] = HEARTBEAT_MSG_ACK;
    if (js.contains("ts"))
    {
        ack["echo_ts"] = js["ts"];
    }
    conn->send(FrameCodec::encode(ack.dump()));
}
```

### 4) 客户端心跳状态与定时线程

```cpp
static const int HEARTBEAT_INTERVAL_SEC = 10;
static atomic_bool g_heartbeatAcked{true};
```

```cpp
static void heartbeatTaskHandler(int clientfd)
{
    while (true)
    {
        this_thread::sleep_for(chrono::seconds(HEARTBEAT_INTERVAL_SEC));

        // 仅登录后发送心跳，避免登录前无意义探测
        if (g_myUserId <= 0)
        {
            continue;
        }

        json hb;
        hb["msgid"] = HEARTBEAT_MSG;
        hb["id"] = g_myUserId;
        hb["ts"] = chrono::duration_cast<chrono::milliseconds>(
            chrono::system_clock::now().time_since_epoch()).count();

        if (!g_heartbeatAcked.load())
        {
            cerr << "[heartbeat] previous heartbeat not acked yet, connection may be unstable" << endl;
        }

        g_heartbeatAcked = false;
        if (sendFrame(clientfd, hb.dump()) == -1)
        {
            cerr << "[heartbeat] send heartbeat failed" << endl;
        }
    }
}
```

### 5) 客户端启动心跳线程

```cpp
std::thread heartbeatTask(heartbeatTaskHandler, clientfd);
heartbeatTask.detach();
```

### 6) 客户端接收心跳 ACK

```cpp
if (HEARTBEAT_MSG_ACK == msgtype)
{
    g_heartbeatAcked = true;
    continue;
}
```

## 对代码的详细解释（重点）

### A. `g_heartbeatAcked` 的语义
- `true`：最近一次心跳已经收到服务端 ACK；
- `false`：最近一次心跳已发出，但尚未收到 ACK。

每轮发送前先检查该值：
- 若还是 `false`，说明“上轮心跳未确认”，链路可能异常，打印告警。

### B. 为什么用独立心跳线程
- 不阻塞主交互线程（命令输入）；
- 不耦合业务消息发送节奏；
- 即使用户不发任何消息，也能持续探测连接活性。

### C. 为什么心跳也走帧协议
项目已统一使用 `[4字节长度 + payload]` 帧协议。
心跳包和业务包共享同一传输通道与编解码路径，避免再引入新通道复杂度。

### D. 为什么服务端心跳处理要“立即应答”
心跳的核心是低延迟探测。服务端不做复杂业务逻辑，只回 ACK：
- 响应快；
- 逻辑简单；
- 便于客户端快速判断连接质量。

### E. `echo_ts` 的作用
服务端回显客户端发送的 `ts`，便于后续扩展：
- 可以计算心跳 RTT；
- 可以用于诊断抖动与延迟。

当前先作为调试辅助字段保留。

### F. 登录/注销状态与心跳联动
- 心跳线程在 `g_myUserId <= 0` 时不发送（登录前/注销后不探测）；
- 注销时将 `g_myUserId = 0`，可自动停止后续心跳发送。

---

## 最终效果

1. 增加了应用层连接活性探测能力；
2. 异常链路可更早暴露，不必等业务消息触发；
3. 为后续自动重连、在线状态灯、RTT 监控打下基础。
