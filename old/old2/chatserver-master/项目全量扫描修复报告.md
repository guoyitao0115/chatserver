## 二、问题A：登录分支无花括号（可维护性/可读性风险）

### 1）问题描述
`login()` 中曾出现 `if (authOk)` 后直接跟 `if (user.getState() == "online")` 的写法。虽然当前语义可执行，但这类写法在后续维护中非常容易因插入语句导致逻辑漂移。

### 2）修复文件与行号
- `src/server/chatservice.cpp`
  - `195`：`void ChatService::login(...)`
  - `222`：`if (authOk)`
  - `224`：`if (user.getState() == "online")`

### 3）修复代码

```cpp
if (authOk)
{
    if (user.getState() == "online")
    {
        // ...
    }
    else
    {
        // ...
    }
}
else
{
    // ...
}
```

### 4）修复说明
- 显式加 `{}` 让分支边界清晰，避免“悬挂 if”造成误读；
- 便于后续继续扩展认证逻辑（风控、限流、MFA）时不引入隐性分支错误；
- 这是工程代码规范中的高优先级可维护性修复。

## 三、问题B：重试日志的并发读取竞争（线程安全问题）

### 1）问题描述
`retryTaskHandler()` 在锁外打印重试日志时，直接访问 `g_pendingRetry[kv.first]`。此时其他线程可能正在 `removePending()` 修改 map，存在并发访问风险。

### 2）修复文件与行号
- `src/client/main.cpp`
  - `15`：新增 `#include <tuple>`
  - `235`：`vector<tuple<string,string,int>> toRetry;`
  - `250`：`int nextRetry = ++cnt;`
  - `272`：`const string &msgId = get<0>(kv);`
  - `277`：`sendFrame(g_retryClientFd, payload);`

### 3）修复代码

```cpp
vector<tuple<string,string,int>> toRetry;

int nextRetry = ++cnt;
toRetry.emplace_back(kv.first, kv.second, nextRetry);

for (auto &kv : toRetry)
{
    const string &msgId = get<0>(kv);
    const string &payload = get<1>(kv);
    int retryCnt = get<2>(kv);
    cerr << "[retry] resending message_id=" << msgId
         << " (retry " << retryCnt << "/" << MAX_RETRY_COUNT << ")" << endl;
    sendFrame(g_retryClientFd, payload);
}
```

### 4）修复说明
- 在持锁阶段就把 `msgId/payload/retryCnt` 拷贝到 `toRetry`；
- 锁外只使用本地快照，不再访问共享 map；
- 保持“锁外发送”设计，避免持锁发送导致阻塞扩大。
