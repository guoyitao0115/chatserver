# 更新项目学习记录

在完成调查并形成可靠结论后、发送最终回复前，把本轮值得长期复习的项目知识沉淀到文档。本 Skill 只授予学习文档的维护权限，不因自身触发而修改业务代码、配置、测试或执行 Git 提交与推送；用户另有明确要求时，按用户授权正常完成任务。

## 工作流程

1. 判断本轮是否产生与当前仓库直接相关、以后仍值得复习的知识：
   - 包括源码实现、架构与调用链、协议与数据流、调试、构建部署、配置、测试、可靠性、优化取舍及面试表达。
   - 不包括闲聊、Skill/插件管理、提示词维护、临时状态、单纯文件整理和普通 Git 操作。
2. 阅读回答所需的源码、配置、测试或运行结果，以当前实现为准；区分已实现事实、推论、缺陷、建议和未验证内容。
3. 先形成准确答案，再读取根目录 `项目学习记录.md`，检查是否已有相同主题。
4. 新知识放到“问答记录”顶部；已有主题则完善原记录，不重复堆叠相同结论。
5. 判断是否需要同步其他文档：
   - 涉及某个源码或配置文件，且现有说明因此错误、不完整或容易误导时，更新其同目录、同名的 `文件名.md` 讲解文档。
   - 涉及整体变更、架构、优化、学习路线、测试或面试表述时，按需更新 `docs/1-项目修改说明.md`、`docs/2-当前项目架构.md`、`docs/3-项目后续提升建议.md`、`docs/4-项目学习指南.md`、`docs/5-简历与面试指南.md`、`docs/6-完整测试与压力测试报告.md`。
   - 只是对现有知识的复习或补充问答时，只更新 `项目学习记录.md`。
6. 使用 `apply_patch` 修改文档。完成后检查新增内容的位置、链接、重复项以及事实状态；运行 `git diff --check`。
7. 完成文档维护后再给出完整答案，并简短说明本轮实际更新了哪些学习文档。

## 学习记录格式

日期采用 `YYYY-MM-DD`，新记录放在旧记录上方：

```markdown
### YYYY-MM-DD｜简短主题

- **问题：** 用一句话概括真正需要理解的内容。
- **结论：** 用一到三句话记录核心答案。
- **理解要点：**
  - 说明关键执行过程、数据变化、模块关系或工程取舍。
  - 记录重要限制、适用边界和实际验证结果。
- **关联内容：** 使用仓库相对路径链接到源码或相关文档；没有具体文件时写“项目整体”。
- **待复习/待验证：** 只写真实遗留项；没有则写“无”。
```

如果文件不存在，初始化为：

```markdown
# 项目学习记录

本文档沉淀学习当前项目时遇到的关键问题和可复用结论，以当前源码和实际验证结果为准。

## 问答记录
```

## 记录与同步规则

- 只记录能够增加、纠正或澄清当前项目知识的内容；通用知识只有在明确结合本项目时才记录。
- 不复制整段对话或大段源码，只保留便于复习的结论、关键过程、限制和链接。
- 不保存密码、令牌、私人地址或其他敏感信息。
- 不编造实现和测试结果。没有查看源码或运行验证时，明确写“未验证”。
- 当前源码与旧文档冲突时，以当前源码为准；历史文档明确属于历史版本时保留历史语境，不把它当成当前实现。
- 建议不能写成“已实现”，偶发现象不能写成确定缺陷，理论能力不能写成实测结果。
- 同名代码讲解文档保持“代码片段后紧跟对应讲解”的既有结构，只更新受本轮结论影响的段落，不做无关扩写。
- 项目文档仅在其事实内容会因本轮结论而过时、冲突或明显缺失时同步，不为了“看起来完整”批量修改。
- Skill 本身不修改业务代码，也不自动暂存、提交或推送；这些操作必须来自用户的明确请求。
- 若本轮没有符合条件的学习结论，不读取或修改学习文档，也不在回复中制造记录流程噪音。
