# `usermodel.hpp` 讲解

## 作用概览

该接口封装用户表的增、查、密码迁移和在线状态更新。

## 按学习顺序讲解

- `insert(user)`：注册时插入用户，并把自增 ID 回填。
- `query(id)`：按 ID 读取用户；不存在时返回默认 `User`。
- `updatePassword(id,pwdHash)`：旧明文用户首次成功登录后升级为 bcrypt。
- `updateState(user)`：把目标用户状态写为 online/offline。
- `resetState()`：服务收到退出信号时把所有 online 改为 offline。

## 函数详细说明

### `insert(user)`

这个函数用于用户注册。参数是 `User&`，因为函数需要读取用户输入的昵称和密码哈希，也需要在插入成功后把数据库生成的用户 ID 回填到对象里。

调用链一般是：客户端发送注册 JSON，`ChatService::reg` 做密码哈希，然后构造 `User` 调用 `UserModel::insert`。如果插入成功，服务端把新 ID 返回给客户端。

返回值表示数据库写入是否成功。失败原因可能是数据库不可用、字段非法、唯一约束冲突等。当前项目只返回统一失败响应，后续可以按错误码细分提示。

### `query(id)`

这个函数按用户 ID 查询用户资料，登录和鉴权相关逻辑都会用到。参数 `id` 来自客户端登录请求或业务操作中的用户 ID。

返回值是 `User`。如果查到用户，就填充 ID、昵称、密码哈希和状态；如果没查到，就返回默认对象，调用方通过 `getId() == -1` 判断不存在。

它是登录链路的核心入口之一：`ChatService::login` 会先 `query`，再用 `PasswordHasher::verify` 校验密码，校验通过才更新在线状态和连接映射。

### `updatePassword(id, pwdHash)`

这个函数用于把用户密码更新为新的哈希值。项目里它主要服务于旧数据迁移：如果数据库里还存在历史明文密码，用户首次使用明文成功登录后，服务端会把它升级成 bcrypt 哈希。

参数 `id` 是目标用户，`pwdHash` 必须是已经生成好的 bcrypt 字符串。函数不负责生成盐或哈希，安全逻辑放在 `PasswordHasher`，数据库模型只负责写入。

返回值是更新是否成功。面试时可以说明：这种“登录时迁移”能兼容旧用户，不需要一次性强制改库，但必须保证迁移后不再把明文写回去。

### `updateState(user)`

这个函数把用户在线状态写回数据库。参数传入完整 `User` 对象，但实际主要使用 `id` 和 `state` 两个字段。

登录成功后会把状态更新为 `online`，正常退出或连接异常关闭后会更新为 `offline`。它让用户列表展示能看到基本在线状态。

当前系统还用 Redis 保存更实时的跨节点路由。面试时不要把数据库状态说成强一致在线判定，它更像持久状态展示；真正投递时还要看连接映射和 Redis。

### `resetState()`

这个函数在服务端退出时把所有在线用户重置为离线。它通常由服务端信号处理函数触发，避免进程崩溃或停止后数据库里残留一批 `online` 用户。

返回值通常不暴露给业务流程，重点是清理全局状态。它只能修复数据库状态，不能清理客户端连接，因为进程退出时连接已经自然断开；也不能替代 Redis TTL，跨节点路由仍然依赖 Redis 自动过期或显式清理。

## 面试重点

重要性中等。常见问题：为什么数据库状态与 Redis 路由并存？数据库便于持久查询，Redis 提供带 TTL 的跨节点原子路由；两者可能短暂不一致，因此登录与断线代码要按持有者条件更新。
