# `friendmodel.hpp` 讲解

## 作用概览

该接口封装好友表操作，使业务层不直接拼接好友 SQL。

## 按学习顺序讲解

- `insert(userid, friendid)`：新增一条从当前用户到目标用户的好友关系。
- `query(userid)`：连接好友表与用户表，返回好友的 ID、昵称和在线状态列表。

## 函数详细说明

### `insert(userid, friendid)`

这个函数在好友关系表中写入一条“`userid` 关注/添加 `friendid`”的关系。调用方通常来自 `ChatService::addFriend`，也就是客户端发起添加好友请求后，业务层把用户 ID 和目标好友 ID 传入模型层。

参数上，`userid` 是发起添加动作的当前登录用户，`friendid` 是被添加的用户。函数本身不负责校验当前用户是否已经登录，也不负责校验目标用户是否存在，这些属于业务层或数据库约束可以进一步补强的部分。

执行流程上，它的实现会拼接 `insert into Friend(userid, friendid)` 语句，然后通过 `MySQL::update` 执行写入。返回值是布尔值，表示 SQL 是否执行成功。当前业务层没有把失败原因细分给客户端，所以如果数据库断开、重复关系、目标用户不存在等情况出现，调用方只能看到成功或失败。

面试追问时要注意：当前设计更接近“单向好友关系”。如果产品语义要求“互为好友”，就应该在同一个事务里插入两条记录，或引入好友申请、待确认、已拉黑等状态字段。

### `query(userid)`

这个函数按用户 ID 查询好友列表。它一般在登录成功时被 `ChatService::login` 调用，用来把好友资料放进登录响应，客户端登录后才能展示好友列表。

参数 `userid` 表示要查询谁的好友。返回值是 `vector<User>`，其中每个 `User` 只需要填好友展示必要字段，例如 ID、昵称和在线状态；密码字段不应该被带到客户端响应里。

执行流程上，实现会把 `Friend` 表和 `User` 表做关联查询：先找到 `userid` 对应的 `friendid`，再读取好友用户资料。这样业务层不用知道两张表之间的连接细节，符合“业务层调接口，模型层管 SQL”的分层方式。

边界点是：好友数量很多时，一次性返回完整列表可能较重，可以改成分页；如果需要双向关系，查询条件也要考虑两条记录或无向关系表结构。

## 面试重点

重要性较低到中等。可能问题：好友关系是单向还是双向？当前是一条单向记录；若需要双向好友，应在事务中插入两条记录，或建“好友申请/关系状态”模型。
