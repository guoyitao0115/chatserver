# `offlinemessagemodel.hpp` 讲解

## 作用概览

该接口负责离线消息持久化，是本地连接和 RabbitMQ 均无法完成投递时的最终兜底。

## 按学习顺序讲解

- `insert(userid, msg)`：插入一条消息并返回成功与否；返回值使业务层只有在真正落库后才发送成功 ACK。
- `query(userid)`：按数据库自增 ID 查询用户全部离线消息，保持写入顺序。
- `remove(userid)`：登录响应装入离线消息后删除该用户的已取消息。

## 函数详细说明

### `insert(userid, msg)`

这个函数把无法实时投递的消息写入离线消息表。`userid` 是最终接收者，`msg` 是完整的业务 JSON 字符串，里面通常包含 `msgid`、发送者、接收者、时间、消息内容、客户端序号等字段。

它的调用位置很关键：单聊或群聊投递时，服务端会先尝试本节点连接直投；如果用户在其他节点，则通过 RabbitMQ 精确路由转发；如果这些路径都不可用，才会调用 `insert` 作为最终兜底。

返回值表示落库是否成功。当前业务层只有在直接投递、跨节点投递或离线落库至少一个路径成功时，才应该给发送端确认成功 ACK，这能减少“客户端以为发成功但服务端没保存”的问题。

### `query(userid)`

这个函数查询用户的离线消息。它通常在 `ChatService::login` 里被调用：用户登录成功后，服务端读取该用户未接收的消息，并塞进登录响应的 `offlinemsg` 数组中。

返回值是 `vector<string>`，每个元素都是原始消息 JSON 字符串。保持原始字符串的好处是简单，离线表不需要理解每种业务消息字段；缺点是数据库无法方便按消息字段建立索引。

实现上应按离线消息表的自增 ID 升序读取，这样同一用户的离线消息能尽量保持写入顺序。需要注意，这只是“数据库写入顺序”，不等价于全局真实发送时间顺序。

### `remove(userid)`

这个函数删除某个用户已经查询出来的离线消息。当前项目是在登录响应组装完成后删除，避免用户下次登录重复收到同一批离线消息。

这个设计简单，但有一个面试高频问题：查询后删除不是端到端确认。如果服务端查出离线消息并删除，但响应还没真正到达客户端就崩溃，消息可能丢失；如果不删除又可能重复收到。更可靠的方案是给离线消息增加状态，客户端收到后按消息 ID ACK，服务端再删除或标记已确认。

## 面试重点

重要性高。可能问题：查询后删除是否绝对不丢不重？不是；响应发送与删除无法原子化，崩溃窗口可能导致丢失或重放。更严格方案是消息状态 + 客户端确认、事务 outbox 或独立消息队列。
