# `msgdedup.hpp` 讲解

## 作用概览

`MsgDedup` 是线程安全的进程内 LRU+TTL 去重器，在 Redis 不可用时仍能阻止短时间内重复处理相同 `message_id`。

## 按学习顺序讲解

### `MsgDedup(maxSize, ttlSeconds)`

保存容量和有效期；默认最多 10000 条、存活 120 秒。

### `isDuplicate(msgId)`

空 ID 为兼容旧客户端始终视为新消息。非空 ID 在锁内查哈希表：未过期则移到 LRU 头并返回重复；已过期则移除；新 ID 插入链表头，超容量时从尾部 O(1) 淘汰。哈希表负责 O(1) 定位，链表负责顺序。

### `forget(msgId)`

投递失败时同时从链表和哈希表删除处理标记，让客户端用同一个 ID 重试。

### `Entry`

记录首次处理时间和链表迭代器，不是函数，但它使移动、删除保持 O(1)。

## 函数详细说明

### `MsgDedup(size_t maxSize, time_t ttlSeconds)`

- **参数**：最大条目数和有效秒数。构造只保存参数，不预分配所有节点。
- **不变量**：`_map` 中每个 ID 都对应 `_lruList` 的一个有效迭代器；链表头最近访问、尾最久未访问。
- **边界**：若把 maxSize 设为 0，首次插入后会立即淘汰；实际项目传入 10000。

### `bool isDuplicate(const string &msgId)`

- 空 ID 不进入缓存且返回 false，这是旧协议兼容，不是可靠模式推荐用法。
- 在唯一互斥锁内读取当前秒级时间，查哈希表：
  - 条目存在且 `now-timestamp < TTL`：把链表节点 splice 到头部，返回 true；访问不会刷新 timestamp，只刷新 LRU 位置。
  - 条目存在但过期：从链表和 map 同时删除，再按新消息处理。
  - 新消息：push_front，并把时间戳与迭代器写入 map。
- 插入后若容量超限，取链表尾 ID，同时从 map/list 删除。
- **复杂度**：平均查找、移动、删除为 O(1)；互斥锁保证并发同 ID 只有一个调用返回“新消息”。
- **语义**：函数把“检查”和“记录已处理”合并成原子临界区，不能拆成两个公开操作，否则会产生 check-then-act 竞态。

### `void forget(const string &msgId)`

- 空 ID 或不存在条目时幂等返回。
- 存在时在同一锁内删除链表节点与哈希项，维持双结构一致。
- 用于业务未真正完成时补偿。它允许之后同 ID 再次成为新消息，但不会通知其他线程或恢复已经发生的部分副作用。


## 面试重点

重要性高。常见问题：为什么同时需要 map 和 list？哈希表快速查找，链表维护 LRU；TTL 与容量各解决什么问题？时间窗口与内存上限；本地去重为何不足？多实例之间不共享，所以正常路径优先 Redis。
