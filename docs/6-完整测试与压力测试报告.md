# ChatServer 完整测试与压力测试报告

## 1. 测试结论

测试日期：2026-07-17。

在本报告描述的环境和负载范围内，项目的构建、核心协议、Web 网关、账户、好友、群组、单聊、群聊、心跳、身份校验、跨节点路由、离线消息、ACK、重试、去重和单发送者顺序测试全部通过。

最终两档主要压力测试结果：

- 单节点直投：200 个同时在线 WebSocket，5,000 条消息，零丢失、零重复、零乱序，吞吐约 11,627.91 条/秒。
- 双节点跨节点：200 个同时在线 WebSocket，5,000 条 RabbitMQ 跨节点消息，零丢失、零重复、零乱序，吞吐约 3,380.66 条/秒。

故障注入结果：

- RabbitMQ 完全停止后，跨节点消息自动降级到 MySQL 离线消息，恢复登录后可以取回。
- MySQL 停止导致离线落库失败时，服务端返回 `ACK_FAIL=2`，不再误报成功；数据库恢复后使用相同 `message_id` 重试成功，并且只保存一份。

测试过程中发现并修复了三个实际问题：跨节点并发重复登录、离线消息查询缺少显式顺序、离线落库失败仍返回成功 ACK。

> 结论边界：测试可以证明这些场景在本次环境和负载下通过，但不能数学证明系统在任意机器故障、网络分区和无限负载下“永不丢失、永不重复”。生产级更强保证仍需要接收端 ACK、持久化 Outbox/Inbox、RabbitMQ 发布确认和手动消费确认，详见第 9 节。

## 3. 测试方法

测试不是只检查 HTTP 状态码，而是使用真实 WebSocket 客户端完成以下链路：

```text
测试客户端
  → WebSocket
  → Node.js 网关
  → 4 字节长度帧 TCP
  → C++ ChatServer
  → Redis 路由与去重
  → RabbitMQ 跨节点 / MySQL 离线存储
  → 接收端
```

每条可靠性测试消息都携带：

- 全局唯一 `message_id`，用于 ACK 对应和重复检测；
- 单发送者递增 `client_seq`，用于检查顺序；
- `sent_at_ms` 和 ISO 时间，用于检查时间单调性和计算延迟；
- 可识别的测试前缀，用于与其他消息隔离。

压力测试同时统计发送数、ACK 数、接收数、唯一消息 ID 数量、额外重复消息、顺序违规数量和端到端延迟分位数。

## 6. 丢失、重复和顺序测试

### 6.1 在线消息

同一发送者连续突发发送 200 条跨节点消息，不等待上一条 ACK。测试同时收集发送端 ACK 和接收端消息，然后按 `message_id`、`client_seq` 和时间戳校验。

结果：

- 发送：200；
- 成功 ACK：200；
- 接收：200；
- 丢失：0；
- 重复：0；
- 顺序违规：0；
- 时间戳逆序：0。

### 6.2 重复重发

相同消息使用完全相同的 `message_id` 连续发送两次。第一次返回 `ACK_OK=0`，第二次返回 `ACK_DEDUP=1`。

结果：接收端只收到一次。单聊和群聊都通过。

### 6.3 离线消息

接收端主动退出后，发送端连续发送 100 条消息；接收端随后重新建立连接并登录，从登录响应中拉取离线消息。

结果：

- 发送：100；
- 成功 ACK：100；
- 恢复：100；
- 丢失：0；
- 重复：0；
- 顺序违规：0；
- 再次登录重复拉取：0。

离线消息查询已改为 `ORDER BY id ASC`，顺序不再依赖 MySQL 未承诺的默认返回顺序。

### 6.4 顺序保证的准确表述

当前验证的是“同一发送者、同一会话”的顺序。TCP 保持单连接字节顺序，消息携带递增 `client_seq`，CLI 对缺口进行短时缓冲，离线消息按数据库自增 ID 返回。

不同发送者并发发送时不存在天然的全局先后顺序；客户端时间也可能不准确。因此不能把当前结果表述成“所有用户的消息严格按全球时间排序”。如果业务需要全局顺序，应由服务端分配会话序号或使用逻辑时钟。

## 7. 故障注入测试

### 7.1 RabbitMQ 中断

步骤：

1. 用户分别登录两个 ChatServer 节点；
2. 完全停止 RabbitMQ 容器；
3. 保持中断窗口后发送跨节点消息；
4. 检查在线接收；若未在线收到，则退出并重新登录检查离线消息。

结果：消息走 `offline-fallback`，发送端收到成功 ACK，接收端重新登录后取回消息，未丢失。

### 7.2 MySQL 中断与恢复

步骤：

1. 接收端退出，使消息必须进入离线库；
2. 停止 MySQL；
3. 发送消息，检查服务端 ACK；
4. 恢复 MySQL；
5. 使用相同 `message_id` 重试；
6. 接收端重新登录并检查副本数。

结果：

- 数据库中断时：`ACK_FAIL=2`；
- 数据库恢复后重试：`ACK_OK=0`；
- 离线消息副本：1；
- 失败处理不会留下去重标记，恢复后相同 ID 可以重试。

### 7.3 陈旧在线状态

故障测试中还模拟了 MySQL 停止期间连接超时，数据库来不及更新离线状态。Redis 路由已正确释放；MySQL 恢复后，该用户可以重新登录并正常退出，陈旧 `online` 状态自动修复。最终数据库中在线用户为 0。

## 9. 不能过度承诺的边界

本次结果支持“在已测试范围内未发生丢失、重复和单发送者乱序”，不应在简历或面试中说成无条件的 exactly-once。

当前仍有以下生产级边界：

1. 在线本地投递的 ACK 表示服务端已接受并写入 TCP 发送缓冲，不等于接收端应用已经展示。
2. RabbitMQ 当前使用自动消费确认，且队列不是持久化业务队列；在“Broker 已接受但目标节点尚未处理”的极小崩溃窗口仍可能丢失。
3. 离线消息随登录响应发出后即从数据库删除，缺少接收端确认；发送后立刻断网存在确认窗口。
4. Redis 去重键 TTL 为 120 秒，超过窗口后再次使用相同 ID 会被当作新消息。
5. 当前保证单发送者顺序，不保证多个发送者之间的全局时间顺序。
6. 压测规模为单机 Docker 环境下 200 个连接、5,000 条突发消息，不能直接外推到百万连接。

若要进一步接近生产级“至少一次投递 + 最终只展示一次”，建议按优先级实现：

1. 增加接收端 `DELIVER_ACK`，离线消息收到确认后再删除；
2. 增加消息表、Outbox/Inbox 和 `message_id` 唯一索引；
3. RabbitMQ 使用 durable exchange/queue、持久化消息、publisher confirm 和 manual ack；
4. 将去重窗口从纯 TTL 升级为数据库唯一约束与 Redis 热缓存组合；
5. 增加 MySQL 连接池、指标采集和持续压测。

## 10. 测试过程中完成的修复

### 10.1 跨节点并发重复登录

原问题：两个节点同时查询到数据库状态为离线，可能同时登录成功。

修复：使用 Redis `SET NX EX` 原子抢占 `userId -> serverId` 路由；心跳只给当前节点持有的路由续期；退出和异常断连只删除属于当前节点的路由，避免旧连接覆盖新会话。

### 10.2 离线消息顺序

原问题：SQL 没有 `ORDER BY`，虽然常见情况下按主键返回，但数据库并不保证。

修复：按离线消息自增 ID 升序读取。

### 10.3 落库失败误报成功

原问题：MySQL 写入失败时只记录日志，发送端仍收到成功 ACK；同时去重键已经写入，原 ID 重试会被跳过。

修复：投递函数返回真实结果；失败时返回 `ACK_FAIL`，撤销 Redis 和本地去重标记；CLI 保留待重试消息，Web 客户端显示“投递失败，正在重试”并继续重试。

## 11. 如何复现

执行完整非破坏性回归和压力测试：

```bash
./scripts/完整回归与压力测试.sh
```

调整压力规模：

```bash
CHAT_LOAD_PAIRS=50 CHAT_LOAD_MESSAGES=100 ./scripts/完整回归与压力测试.sh
```

也可以分别执行：

```bash
docker compose up -d --build --wait
npm test --prefix web
docker compose exec -T chatserver-1 ctest --test-dir /app/build --output-on-failure
node web/test/full-stack.mjs
node web/test/reliability.mjs
CHAT_LOAD_PAIRS=100 CHAT_LOAD_MESSAGES=50 node web/test/load.mjs
# 同节点本地直投
CHAT_E2E_PORT_2=8080 CHAT_LOAD_PAIRS=100 CHAT_LOAD_MESSAGES=50 node web/test/load.mjs
```

故障注入脚本位于：

- `web/test/chaos-rabbitmq.mjs`
- `web/test/chaos-mysql.mjs`

这两个脚本需要在其输出准备提示后，由另一个终端停止或恢复对应的 Docker 服务，不建议放入普通 CI 自动执行。
