## 一、项目一句话总结

这是一个基于 Muduo 的分布式聊天系统，围绕“消息可靠性、顺序性、多节点通信、安全性、可维护性”持续迭代，形成了完整的工程化改造链路。

---

## 二、核心技术架构

- 网络通信：Muduo TCP 长连接；
- 协议层：自定义帧协议（长度头 + JSON payload）；
- 数据层：MySQL（用户/好友/群/离线消息）；
- 缓存与去重：Redis（`SET NX EX`）；
- 消息总线：RabbitMQ（跨节点转发，方案A 等价迁移）；
- 客户端机制：ACK、pending、超时重试、心跳；
- 安全：bcrypt（随机盐）密码哈希。

---

## 三、关键问题与改造脉络（按演进顺序）

## 1）消息传输稳定性：帧协议
- 解决 TCP 粘包拆包导致 JSON 解析错位问题；
- 客户端与服务端统一采用 `[4字节长度 + payload]`。

## 2）消息可靠性：ACK + pending + 超时重试
- 客户端发送消息后进入 pending；
- 服务端处理后返回 `MSG_ACK`；
- 客户端后台线程按超时重试，达到上限后告警。

## 3）重复消息控制：Redis 优先去重
- 核心命令：`SET key 1 EX ttl NX`；
- Redis 正常时跨实例共享去重状态；
- Redis 异常时回退本地 LRU+TTL 去重兜底。

## 4）消息有序展示：按目标维度序号
- 单聊：按 `toid` 维护客户端序号；
- 群聊：按 `groupid` 维护客户端序号；
- 接收端按会话桶缓冲并连续冲刷，避免跨会话打洞。

## 5）全局唯一消息ID：Snowflake
- `message_id` 升级为 64 位分布式 ID；
- 提升唯一性、趋势有序性和日志追踪能力；
- 保持 ACK/重试/去重链路兼容。

## 6）长连接活性探测：应用层心跳
- 客户端定时发送 `HEARTBEAT_MSG`；
- 服务端立即回 `HEARTBEAT_MSG_ACK`；
- 使“静默连接”状态可感知，便于后续自动重连。

## 7）跨节点通信升级：RabbitMQ 替换 Redis Pub/Sub（方案A 等价迁移）
- 使用固定 fanout exchange：`chat_cross_server`；
- 每实例独占队列并绑定 exchange，广播消费；
- 到达业务层后按“本地是否在线”过滤投递。

## 8）账号安全升级：bcrypt（随机盐）
- 注册改为哈希入库；
- 登录改为 bcrypt 校验；
- 历史明文账号登录成功后平滑迁移。

---

## 四、项目当前能力边界（真实可讲）

1. 已具备客户端->服务端方向的 ACK 闭环；
2. 服务端->接收端的严格“端到端 ACK”尚可进一步增强；
3. RabbitMQ 方案A为最小改造策略，存在一定广播消费开销；
4. 整体已具备较强实习面试含金量。

---

## 五、工程权衡与设计思想

1. **最小侵入优先**：优先改关键链路，不大拆架构；
2. **可靠性优先**：失败时优先降级而不是中断；
3. **兼容优先**：历史数据（明文密码）采用平滑迁移；
4. **可观测优先**：关键路径增加日志和状态码。

---

## 六、整体成果总结

通过连续改造，项目从“可运行聊天系统”升级为“具备分布式可靠性思维与工程质量意识的 IM 系统”：
- 协议更稳；
- 消息更可靠；
- 顺序更可控；
- 跨节点更可用；
- 账号更安全；
- 面试可讲述性更强。
