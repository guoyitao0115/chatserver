# 文档1：项目修改说明

## 1. 修改目标

本轮以根目录主项目为唯一开发版本，参考 `old/` 中的历史实现和原有优化建议，目标是：

1. 保留 Muduo + JSON + 四字节长度帧的核心架构；
2. 修复真实的安全、并发和可靠性问题；
3. 用独立适配层增加 Web 前端，避免改动 C++ 业务协议；
4. 建立可复现的双节点运行环境和自动化测试；
5. 删除“为了堆技术而堆技术”的做法，明确当前能力边界。

历史目录未修改，不参与构建。

## 2. 主要修改

### 2.1 构建与运行

- 将 CMake 调整为 C++17、目标级头文件和依赖配置；
- 增加 `CHAT_BUILD_SERVER`、`CHAT_BUILD_CLIENT`、`CHAT_BUILD_TESTS` 开关；
- 构建产物统一写入构建目录，不再污染源码目录；
- `autobuild.sh` 不再先清空整个 `build/`；
- 增加 Dockerfile、双节点 `compose.yaml` 和 MySQL 初始化脚本；
- 增加 `.gitignore`、`.env.example` 和根目录 README。

### 2.2 协议与连接安全

- 抽出无 Muduo 依赖的 `frameprotocol.hpp`，服务端和客户端共用帧长度规则；
- 拒绝空帧和超过 4 MB 的帧；
- 只收到 1～3 字节帧头时也会进入半包超时统计；
- 服务端 45 秒无任何业务或心跳流量时主动断开空闲连接；
- JSON 必须是对象且包含整数 `msgid`，否则返回统一 `ERROR_MSG`；
- `ERROR_MSG` 添加在枚举末尾，不改变原有消息编号。

### 2.3 身份认证

原实现直接信任消息里的 `id`，客户端登录后仍可把 `id` 改成其他用户，冒用身份发送消息或操作关系。

现在服务端维护两张内存表：

- `userId -> TcpConnection`：向本节点在线用户投递；
- `connectionName -> userId`：验证当前连接实际登录的用户。

单聊、群聊、好友、群组、注销和心跳均校验“声明 ID = 登录 ID”。不一致时返回 401 错误，不进入业务处理。

### 2.4 并发修复

- C++ 客户端的交互线程、重试线程和心跳线程通过互斥锁串行写 socket，防止两个帧交叉；
- Redis 同步连接增加互斥保护；hiredis 同步上下文不再被四个 IO 线程并发调用；
- RabbitMQ 发布连接增加互斥保护；
- RabbitMQ 消费回调先注册、后启动消费线程；
- 本地连接表只在锁内查找和复制连接，实际 `send` 在锁外执行；
- 客户端用条件变量替代已过时的匿名信号量。

### 2.5 消息顺序与心跳

- 保留“按单聊对象或群组分别递增 `client_seq`”的方案；
- 当序号洞超过 2 秒或单会话积压 100 条时，跳过缺失区间并继续显示，解决永久队头阻塞；
- 服务端除响应客户端心跳外，新增空闲连接巡检；
- 心跳同时刷新 Redis 中的用户路由 TTL。

该顺序方案只保证单个发送者在单个会话内的显示顺序，不声称提供分布式全局顺序。

### 2.6 数据与配置

- MySQL、Redis、RabbitMQ 地址和凭据支持环境变量；
- 数据库字符集由 GBK 改为 `utf8mb4`；
- 数据库失败日志不再输出完整 SQL，避免泄露密码哈希和聊天内容；
- 动态生成离线消息 SQL，去掉固定 4 KB 缓冲区截断风险；
- 修复用户查询无结果时 `MYSQL_RES` 未释放的问题；
- Redis 删除未使用的 Pub/Sub 线程，只负责去重与在线路由；
- RabbitMQ 发布端启用 publisher confirm 和 mandatory 路由检查，连接/确认/无路由
  失败时跨节点投递同步写离线表；
- 每个节点使用固定 durable 队列和持久消息；消费成功后手动 ACK，业务处理失败时
  NACK 并重新入队；
- RabbitMQ 发布连接在下一次发送时自动重建，消费线程断线后每秒尝试重连；
- Redis `SET NX` 原子抢占登录路由，避免两个节点同时登录同一账号；
- 离线消息按自增 ID 显式升序查询；
- 离线落库失败返回 `ACK_FAIL`，撤销去重标记并允许相同消息 ID 重试。
- CLI 和 Web 接收端使用有界 `message_id` 集合去重，避免 manual ACK 重投或
  confirm 超时后的在线/离线双路径副本重复展示。

### 2.7 RabbitMQ 可靠性补强（2026-08-02）

本次在不改变 `ChatService::deliverMsg()` 路由顺序的前提下完善 MQ 适配层：

1. 每次发布同步等待最多 3 秒的 broker confirm；
2. `mandatory=1`，目标节点队列不存在时通过 `Basic.Return` 判定发布失败；
3. 消息设置 `delivery_mode=2`，节点队列固定为 `chat.server.<serverId>` 并持久化；
4. 消费端 `no_ack=0`，只有本地发送或离线落库成功才手动 ACK；
5. 业务处理失败则 NACK/requeue，连接错误由消费线程自动重连；
6. 发布失败仍沿用现有 MySQL 离线兜底，离线落库也失败才返回 `ACK_FAIL`；
7. 接收客户端按 `message_id` 去重，覆盖 RabbitMQ 重投和确认结果不确定造成的重复。

### 2.8 账户输入

- 注册昵称长度：1～50 字节；
- bcrypt 密码长度：6～72 字节；
- 保留旧明文密码首次登录后自动升级 bcrypt 的兼容逻辑。

## 3. Web 前端方案

新增 `web/`，包括：

- 原生 HTML/CSS/JavaScript 聊天界面；
- Node.js WebSocket/TCP 网关；
- 登录、注册、好友、群组、单聊、群聊、ACK、重试和心跳；
- 响应式布局和基础可访问性；
- 网关集成测试。

选择独立网关而不是让 C++ 服务直接实现 HTTP/WebSocket，原因是：

1. 浏览器无法连接原始 TCP；
2. 网关只做协议转换，原有业务代码无需复制；
3. 出现前端问题不会影响 C++ 核心；
4. 后续可独立替换为 Nginx、Go 或成熟网关。

## 4. 兼容性变化

- 未登录连接不能发送聊天、好友、群组、注销和心跳请求；
- 消息里的用户 ID 必须与当前连接的登录用户一致；
- 新注册密码至少 6 位；
- 空帧视为协议错误；
- 新增 `ERROR_MSG = 14`；原有消息编号不变。

## 6. 本轮有意未做

- 没有同时保留 Kafka 与 RabbitMQ；当前只使用 RabbitMQ；
- 没有将项目拆成微服务；当前规模下拆分只会增加复杂度；
- 没有宣称“消息绝不丢失”或“严格 Exactly Once”；当前是 ACK、去重和离线兜底组合；
- 没有加入复杂前端框架；当前页面较小，原生实现更容易运行和讲解；
- 性能数据只引用 `docs/6-完整测试与压力测试报告.md` 中的实测环境和规模，不外推为百万连接能力。
