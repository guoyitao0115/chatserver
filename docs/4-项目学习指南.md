# 文档4：项目学习指南

## 1. 先运行，再读代码

准备 Docker Desktop 和 Node.js 20+：

```bash
docker compose up -d --build --wait
node web/test/full-stack.mjs
```

看到 `status: passed` 后，浏览器打开：

- <http://localhost:8080>
- <http://localhost:8081>

这两个页面分别连接两个 ChatServer 节点，适合观察跨节点聊天。

停止：

```bash
docker compose down
```

## 2. 推荐阅读顺序

### 第一步：协议

阅读：

1. `include/public.hpp`：有哪些消息；
2. `include/frameprotocol.hpp`：如何编码长度头；
3. `include/server/framecodec.hpp`：Muduo Buffer 如何解出完整帧。

需要理解：TCP 是字节流，没有“消息边界”。一次读取可能是半条、一条或多条业务消息。

### 第二步：网络入口

阅读 `src/server/chatserver.cpp`：

- 连接建立与断开；
- `onMessage`；
- 半包追踪；
- 空闲连接检测；
- JSON 校验和 handler 分发。

尝试回答：为什么业务层不应该直接操作 Muduo Buffer？

### 第三步：业务层

阅读 `src/server/chatservice.cpp`：

- handler 表如何减少大段 `switch`；
- 登录后如何绑定连接身份；
- 单聊与群聊如何复用 `deliverMsg`；
- ACK、去重、RabbitMQ 和离线兜底如何组合。

### 第四步：数据层

阅读 `src/server/model/` 和 `docker/mysql/init.sql`：

- 用户、好友、群组和离线消息的表关系；
- 为什么字符串必须转义或使用 prepared statement；
- 为什么“建群”和“加入创建者”最好用事务。

### 第五步：集群通信

阅读：

- `src/server/redis/redis.cpp`；
- `src/server/mq/rabbitmq_bus.cpp`；
- `compose.yaml`。

重点区分：

- Redis 保存“人在哪个节点”；
- RabbitMQ 把消息发到那个节点；
- MySQL 在人不在线时保存消息。

### 第六步：客户端可靠性

阅读 `src/client/main.cpp`：

- `message_id`；
- pending map；
- ACK 清理；
- 超时重试；
- 心跳；
- 每会话序号与超时冲刷。

### 第七步：Web 接入

阅读：

- `web/gateway.mjs`；
- `web/public/app.js`。

浏览器不能发原始 TCP，网关把 WebSocket 文本帧变成原有 TCP 长度帧，反向也一样。网关不判断用户是否有权限，权限仍由 C++ 服务端判断。

## 3. 核心知识点

### 3.1 粘包和拆包

错误思路：一次 `recv` 就是一条 JSON。

正确思路：

1. 先等待 4 字节长度头；
2. 解析 payload 长度；
3. 数据不足时保留在 Buffer；
4. 数据足够时取出一帧；
5. 继续循环处理后续帧。

### 3.2 ACK、重试和幂等

只重试会产生重复消息，只去重又不能处理网络丢包。三者需要一起设计：

```text
唯一消息ID + 超时重试 + 服务端去重 + ACK
```

这通常得到“至少一次发送、业务效果尽量一次”。

### 3.3 消息顺序

不要一上来追求全局顺序。先定义语义：

- 谁生成序号；
- 哪些消息可以比较；
- 丢了一条要等多久；
- 超时后跳过还是永远阻塞。

本项目选择“每个发送者、每个会话单独排序，洞等待 2 秒”。

### 3.4 在线状态

在线不是一个永久布尔值，而是有租约的状态：

- 登录写路由；
- 心跳续租；
- 正常退出删除；
- 异常断开删除；
- 最坏情况下由 TTL 自动过期。

### 3.5 并发安全

重点检查共享对象是否支持并发：

- `unordered_map` 需要锁；
- 一个 socket 上多个线程写需要按帧串行；
- hiredis 同步连接不能并发用；
- rabbitmq-c 同一发布连接需要串行；
- 不要持有业务锁执行可能变慢的网络发送。

## 4. 测试怎么读

### C++ 核心测试

`test/core_tests.cpp` 验证：

- 长度帧编码与边界；
- LRU 去重与淘汰；
- 环境变量解析。

### 网关集成测试

`web/test/gateway.test.mjs` 启动模拟 TCP 服务，验证：

- HTTP 健康检查；
- WebSocket 握手；
- WebSocket → TCP 帧；
- TCP 帧 → WebSocket；
- 非法消息不会进入后端。

### 全链路测试

`web/test/full-stack.mjs` 使用真实 MySQL、Redis、RabbitMQ 和两个 C++ 节点，验证注册、登录、跨节点聊天、ACK、身份冒用拦截、心跳和离线消息。

## 5. 推荐练习

1. 把帧头拆成 1、1、2 字节发送，观察服务端最终组帧；
2. 连续发送两个完整帧，验证一次回调可处理多帧；
3. 重复发送相同 `message_id`，观察 `ACK_DEDUP`；
4. 关闭 Redis，再发重复消息，验证本地 LRU 回退；
5. 让两个浏览器连接不同节点，观察 RabbitMQ 跨节点投递；
6. 修改消息中的 `id` 冒用别人，验证 401；
7. 让接收方退出后发送消息，再登录观察离线消息；
8. 故意缺少一个 `client_seq`，观察 2 秒后顺序缓冲继续输出。


## 7. 学习完成标准

不要以“代码看完”为标准。能够独立回答以下问题才算掌握：

1. TCP 为什么会粘包和拆包？
2. ACK 丢了为什么不会重复投递？
3. Redis 和 RabbitMQ 在本项目中分别做什么？
4. 用户跨节点在线时，消息经过哪些组件？
5. MQ 或 Redis 故障时系统如何退化？
6. 为什么不能相信客户端上传的用户 ID？
7. 当前方案在哪些情况下仍可能丢消息？
8. 为什么 Web 前端需要适配网关？
