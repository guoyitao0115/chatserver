## 一、30秒自我介绍版

我做了一个基于 Muduo 的分布式聊天系统，重点做了工程化升级：
- 用帧协议解决 TCP 粘包拆包；
- 做了 ACK + pending + 超时重试保障消息可靠性；
- 用 Redis `SET NX EX` + 本地兜底实现幂等去重；
- 引入 Kafka 做跨节点消息转发；
- 用 Snowflake 统一 message_id；
- 增加应用层心跳；
- 将密码从明文升级为 bcrypt（随机盐）并支持历史账号平滑迁移。

整体把项目从“能聊天”升级到“可靠、可扩展、可面试讲深度”的工程版本。

## 二、2分钟 STAR 版（主推）

### S（Situation）
原始聊天系统能跑通，但存在典型工程问题：
- TCP 粘包拆包导致解析不稳定；
- 无完整可靠性闭环；
- 多节点下重复处理和跨服链路可靠性不足；
- 静默连接不可感知；
- 密码明文存储有安全风险。

### T（Task）
在不推翻架构的前提下，低侵入提升系统在可靠性、分布式能力和安全性方面的表现。

### A（Action）
我按链路逐步改造：
1. 协议层：统一帧协议（长度头+payload）；
2. 可靠性：ACK + pending + 超时重试；
3. 幂等：Redis 去重，失败回退本地 LRU；
4. 顺序：发送端按目标维度生成序号，接收端缓冲重排；
5. 分布式：跨服总线从 Redis Pub/Sub 升级到 Kafka（方案A）；
6. 安全：注册/登录改为 bcrypt，老账号登录后自动迁移；
7. 质量：修复并发访问细节和分支可维护性问题。

### R（Result）
- 消息链路更稳定，重试与去重闭环更完整；
- 跨节点通信可靠性提升；
- 连接活性可探测，用户体验更稳；
- 密码安全达到主流工程实践；
- 项目具备“问题-方案-权衡-结果”的完整面试叙事。

## 三、5分钟深挖提纲（面试官追问时）

1. **为什么先做 at-least-once + 幂等，而不是 exactly-once？**
   - 工程性价比最高，复杂度可控，先解决 80% 可靠性问题。

2. **Kafka 方案A为什么可行？**
   - 这是最小改造路径：先拿到持久化和 ACK 可靠性，再逐步演进精确路由。

3. **去重为什么是 Redis + 本地兜底？**
   - Redis 负责跨实例共享；本地兜底保证 Redis 异常时服务不完全失效。

4. **顺序显示为什么按目标维度分序号？**
   - 避免发送者全局序号跨会话打洞导致重排阻塞。

5. **bcrypt 改造亮点是什么？**
   - 不只是哈希，还做了历史明文账号平滑迁移，降低上线风险。
