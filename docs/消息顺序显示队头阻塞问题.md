# 消息顺序显示队头阻塞（HOL Blocking）问题

## 一、问题描述

当前客户端实现了"按 `client_seq` 顺序展示消息"的缓冲机制，但存在**队头阻塞（Head-of-Line Blocking）**问题：

若某条消息因网络丢失、服务端异常等原因永远不到达，其后续所有消息将永久堆积在缓冲区，**永远不会被展示**。

---

## 二、问题位置

**文件**：`src/client/main.cpp`

**关键数据结构**（约第 330 行）：

```cpp
// 每个会话最后已显示的 client_seq
static unordered_map<string, uint64_t> g_lastShownSeq;
// 乱序缓冲：key=session, value=(seq -> message)
static unordered_map<string, map<uint64_t, string>> g_orderBuffer;
```

**问题核心逻辑**（约第 360-395 行，`printOrderedIncoming` 函数）：

```cpp
while (!buf.empty())
{
    auto it = buf.begin();
    if (it->first == last + 1)   // 严格要求"恰好下一条"
    {
        cout << it->second << endl;
        last = it->first;
        buf.erase(it);
    }
    else
    {
        break;  // <-- 问题所在：有"洞"时直接停止，永远等待前驱
    }
}
```

---

## 三、问题复现场景

假设发送方对同一接收者依次发出消息 seq=1, 2, 3, 4, 5, 6：

- 接收方收到 seq=1, 2, 3, 4（正常显示到 4）
- seq=5 因网络丢失永远未到达
- 接收方收到 seq=6, 7, 8 …
- 结果：6, 7, 8 全部堆在 `g_orderBuffer` 中，**永远不显示**

---

## 四、影响分析

| 场景 | 影响 |
|------|------|
| 局域网本机测试 | 几乎不触发（丢包概率极低）|
| 弱网/跨公网 | 有实际触发风险 |
| 服务端进程崩溃后重启 | 可能触发（部分消息未投递）|
| 面试讲解可靠性设计时 | 是一个需要主动说明的设计权衡 |

---

## 五、解决方案

### 方案：超时强制冲刷（推荐）

等待超过一定时间（如 2 秒）仍无法推进时，强制跳过"洞"，从当前 buffer 最小 seq 开始继续显示。

**新增数据结构**：

```cpp
// 记录每个 session 的 buffer 首次阻塞时间，用于超时冲刷
static unordered_map<string, chrono::steady_clock::time_point> g_orderBufferStallTime;
static const int ORDER_FLUSH_TIMEOUT_MS = 2000; // 等待超过 2 秒强制跳过
```

**修改后的 `printOrderedIncoming` 冲刷逻辑**：

```cpp
auto &buf = g_orderBuffer[key];
while (!buf.empty())
{
    auto it = buf.begin();
    if (it->first == last + 1)
    {
        cout << it->second << endl;
        last = it->first;
        buf.erase(it);
        g_orderBufferStallTime.erase(key); // 推进成功，重置超时计时
    }
    else
    {
        auto &stallTime = g_orderBufferStallTime[key];
        auto now = chrono::steady_clock::now();
        if (stallTime == chrono::steady_clock::time_point{})
        {
            // 首次卡住，开始计时
            stallTime = now;
        }
        else if (chrono::duration_cast<chrono::milliseconds>(now - stallTime).count()
                 >= ORDER_FLUSH_TIMEOUT_MS)
        {
            // 超时：跳过丢失的序号，从最早有消息处继续
            cout << "[提示: 消息序号 " << (last + 1) << " 未收到，已跳过]" << endl;
            last = it->first - 1; // 从当前最小seq接续
            stallTime = {};        // 重置计时器
            continue;              // 重新进入 while 循环
        }
        break;
    }
}
```

---

## 六、方案权衡

| 维度 | 当前实现 | 超时冲刷方案 |
|------|----------|--------------|
| 顺序保证 | 严格 | 超时后降级为尽力而为 |
| 消息丢失时的表现 | 永久阻塞后续消息 | 等待 2 秒后自动跳过 |
| 实现复杂度 | 低 | 低（仅增加计时逻辑）|
| 用户体验 | 丢消息后界面卡死 | 丢消息后给出提示并继续 |
