# 文档5：简历写法与面试指南

## 1. 项目定位

推荐名称：**基于 Muduo 的集群即时通信系统**。

一句话介绍：

> 使用 C++17 和 Muduo 实现 TCP 长连接聊天服务，以 MySQL 持久化业务数据、Redis 维护在线路由和幂等键、RabbitMQ direct exchange 完成跨节点定向投递，并通过轻量 WebSocket/TCP 网关提供浏览器客户端。

不要说成“生产级微信”或“百万并发系统”。当前项目更准确的定位是：有完整链路、能运行、能测试、能讨论工程取舍的后端项目。

## 2. 简历项目描述

### 版本 A：四条精简版

**基于 Muduo 的集群即时通信系统｜C++17、MySQL、Redis、RabbitMQ、WebSocket**

- 基于 Muduo 多 Reactor 线程模型实现 TCP 长连接服务，设计“4 字节长度头 + JSON”应用层帧协议，解决粘包、拆包、超大帧与慢速半包问题。
- 为消息链路加入唯一消息 ID、ACK、超时重试、Redis/LRU 去重及接收端最终去重；
  RabbitMQ direct 使用持久节点队列、publisher confirm、手动消费 ACK 和断线重连，
  发布失败时降级保存离线消息。
- 修复客户端身份冒用、共享 socket 并发写帧、hiredis/rabbitmq-c 连接并发访问等问题；增加 WebSocket/TCP 适配网关和 Docker Compose 全链路测试，覆盖跨节点聊天、心跳、离线消息与认证拦截。
- 在单机 Docker 双节点环境建立 200 个 WebSocket、5,000 条消息的历史压测基线；
  RabbitMQ confirm 改造后的跨节点吞吐仍需复测，简历暂不引用旧跨节点数字。

### 版本 B：五条详细版

- 使用 C++17、Muduo 和 handler 映射实现登录、注册、好友、群组、单聊与群聊，网络层和业务层解耦。
- 设计长度帧协议，利用 Muduo Buffer 增量解码；增加 4 MB 上限、10 秒半包超时和 45 秒空闲连接巡检。
- 组合消息 ID、ACK、3 次超时重试、Redis 分布式去重和本地 LRU 去重，降低 ACK 丢失造成的重复投递。
- 使用 Redis 保存 `userId -> serverId` 租约，RabbitMQ direct routing key 定向投递；
  结合 publisher confirm、manual ACK、持久队列和断线重连，失败时落离线库兜底。
- 设计零业务侵入的 WebSocket/TCP 网关；通过双 ChatServer 节点、MySQL、Redis、RabbitMQ 的容器化环境完成自动注册、登录、跨节点消息、身份冒用、心跳和离线消息全链路验证。

简历只选 3～4 条，不要把所有技术都塞进去。

## 3. STAR 表述

### S：背景

原版项目能完成基础聊天，但把一次 TCP 读取当成一条 JSON，跨节点依赖广播，密码和在线状态处理较简单，也缺少可靠性测试。在面试中又被连续问到粘包、重试、去重、顺序、心跳、密码安全和 MQ 选型。

### T：任务

在不推翻 Muduo 网络核心的前提下，补齐协议边界、可靠投递、集群路由、安全认证和可运行验证，并让项目可以被浏览器直接体验。

### A：行动

1. 用长度头解决 TCP 消息边界；
2. 用消息 ID + ACK + 重试 + Redis/LRU 去重处理重复；
3. 用 Redis 路由和 RabbitMQ direct exchange 代替广播；
4. 绑定连接与用户身份，阻止伪造 ID；
5. 对共享 socket、Redis 和 RabbitMQ 连接增加并发保护；
6. 用独立网关接入 WebSocket；
7. 为 RabbitMQ 增加 confirm、manual ACK、持久队列、断线重连和接收端去重；
8. 构建双节点容器环境和全链路测试。

### R：结果

项目可通过一条命令启动完整依赖；历史自动化测试已验证 C++ 构建、WebSocket/TCP
转换、跨节点投递、ACK、认证、心跳和离线消息。RabbitMQ confirm 改造后已完成客户端、
核心和 Web 单元测试，但当前环境未完成新的双节点回归，因此旧跨节点吞吐只作为历史基线。

引用性能数字时必须同时说明“单机 Docker、200 连接、5,000 条消息”的环境和规模，不把它外推为百万连接或生产 SLA。

## 4. 项目亮点怎么讲

### 4.1 亮点不是“用了很多中间件”

更好的表达：

> 我先定义每个组件的职责。Redis 只保存短期幂等键和用户所在节点，RabbitMQ 只负责节点间消息转发，MySQL 只负责业务持久化。这样出现故障时可以明确知道在哪里降级。

### 4.2 可靠性是组合方案

> 客户端可能因为 ACK 丢失而重发，所以服务端不能简单再次投递。我给每条业务消息分配唯一 ID，客户端超时重试，服务端用 Redis 原子写去重；Redis 不可用时回退本地 LRU。这个方案的准确表述是至少一次发送加幂等处理，不是 Exactly Once。

### 4.3 集群投递从广播改为定向

> 用户登录时把 `userId -> serverId` 写入 Redis，消息发送节点先查目标节点，再使用 RabbitMQ direct routing key 投递。节点数量增加时，每条消息仍只发送给一个目标节点；目标刚下线或发布失败时写离线库。

### 4.4 安全问题来自“不能相信客户端”

> 原实现只读取 JSON 里的用户 ID，攻击者可以修改 ID 冒用他人。我增加 connection 到 userId 的反向绑定，所有登录后操作都比较声明 ID 和认证 ID。全链路测试会主动伪造 ID，并断言服务端返回 401。

### 4.5 前端以适配层接入

> 浏览器不能连接原始 TCP。我没有把 HTTP/WebSocket 塞进聊天核心，而是增加一个无业务状态的网关，只转换 WebSocket 与原有长度帧。这样 C++ 服务协议不变，前端接入也能独立演进。

## 5. 历次面试问题与建议回答

以下问题来自原版及各次修改，应全部会讲，但不需要把每一项都写到简历。

### 5.1 TCP 粘包和拆包

**问：为什么一次 `recv` 不能直接解析 JSON？**

TCP 是字节流，不保留发送边界。一次读取可能只有半条消息，也可能包含多条消息。

**方案：**固定 4 字节大端长度头，Muduo Buffer 数据不足就等待，足够就循环取帧。增加 4 MB 上限，防止恶意长度撑爆内存。

**追问：只收到 2 字节帧头怎么办？**

保留在 Buffer，同时从第一个未完成字节开始计时；超过 10 秒仍未完整则断开，防止慢速半包占用连接。

### 5.2 ACK 和重试

**问：发送成功为什么还需要 ACK？**

`send` 成功只表示数据进入本机内核缓冲区，不代表服务端业务已接受。业务 ACK 让发送方知道何时清理 pending。

**问：ACK 丢了会怎样？**

发送方重试相同 `message_id`，服务端识别重复并返回 `ACK_DEDUP`，不重复投递。

### 5.3 消息 ID 与 Snowflake

**问：为什么需要全局唯一 ID？**

ID 是 ACK 关联、超时重试、幂等去重和日志追踪的基础。

C++ 客户端使用 Snowflake，Web 客户端使用 UUID。项目并不依赖 ID 的具体算法，只依赖在去重窗口内唯一。

**问：Snowflake 的问题？**

需要唯一 workerId，时钟回拨要处理，部署配置错误会冲突。若业务不需要趋势递增，UUID 更简单。

### 5.4 Redis 去重与本地 LRU

**问：为什么不能只用内存 set？**

多节点不共享，服务重启后丢失，而且无限增长。本地实现使用容量上限和 TTL，但只作为 Redis 故障回退。

**问：Redis 命令为什么用 `SET NX EX`？**

判断与写入是一个原子命令，避免并发客户端都判断“不存在”后同时处理。

### 5.5 消息顺序

**问：如何保证消息顺序？**

先定义范围。本项目只在“同一发送者、同一会话”内按 `client_seq` 展示，不保证多发送者全局顺序。

**问：序号 N 永远没到怎么办？**

原版本会发生 HOL Blocking，N+1 之后永久等待。现在等待 2 秒后跳过缺失区间继续显示，同时记录提示。可用性优先于无限等待。

### 5.6 心跳

**问：TCP 有 keepalive，为什么还做应用层心跳？**

系统 keepalive 默认检测时间可能很长，也不了解登录会话。应用层心跳可以用更短周期刷新在线租约并验证业务链路。

当前客户端每 10 秒发送心跳，Redis 路由 TTL 为 120 秒，服务端 45 秒无流量断开连接。

### 5.7 Redis Pub/Sub、Kafka、RabbitMQ 怎么选

**历史过程：**原版 Redis Pub/Sub → 曾尝试 Kafka → 当前 RabbitMQ direct。

面试表述：

- Redis Pub/Sub 简单，但没有持久化和消费确认，广播模式浪费；
- Kafka 适合高吞吐日志流和可回放事件，但点对点低延迟路由需要额外 topic/partition 设计，对该项目偏重；
- RabbitMQ 原生 exchange/routing key 更贴合“把消息发到目标服务节点”的需求。

不要说 RabbitMQ 在所有场景都优于 Kafka。选型取决于消息模型。

### 5.8 为什么 direct，不用 fanout

fanout 会让每个节点都消费每条消息，再判断是否属于自己，开销随节点数增长。direct 使用目标 `serverId` 作为 routing key，只投递到一个节点。

### 5.9 RabbitMQ 故障怎么办

发布端使用 `mandatory + publisher confirm`：无目标队列、broker NACK、确认超时或
连接错误都返回失败，由业务层同步写离线表。消费端只有在本地发送或离线落库成功后
才手动 ACK，失败则 NACK/requeue；发布和消费连接断开后都会重建。

仍要诚实说明：confirm 只证明 broker 接受并路由消息，不代表接收客户端处理成功；
本地 TCP 发送后、消费 ACK 前断线可能重投，所以客户端还要按 `message_id` 去重。
下一步是接收端送达 ACK、有限重试和死信队列。

### 5.10 bcrypt 和明文迁移

**问：为什么不能直接 SHA-256？**

通用哈希太快，密码泄露后适合暴力破解。bcrypt 自带盐且计算成本可配置。

**问：旧明文用户怎么办？**

登录时识别哈希前缀；旧账户先按明文校验，成功后立即生成 bcrypt 哈希并回写，逐步迁移。

### 5.11 SQL 注入

聊天内容、昵称、群描述和密码都不能直接拼 SQL。当前先使用 `mysql_real_escape_string` 修复，并去掉敏感 SQL 日志；更推荐 prepared statement，这是下一步改进。

### 5.12 并发安全

**问：哪些地方存在数据竞争？**

- 在线连接表；
- 同一个客户端 socket 被心跳、重试、主线程同时写；
- hiredis 同步连接被多个 IO 线程使用；
- rabbitmq-c 发布连接被多个线程使用。

解决方法是锁住共享状态或连接，但网络发送尽量放到业务锁外，缩短临界区。

### 5.13 离线消息语义

**问：当前离线消息一定不丢吗？**

不能这样承诺。当前能在用户离线、路由缺失或 MQ 发布失败时落 MySQL，并在登录时返回；但登录响应后立即删除仍有确认窗口，下一步需要离线消息 ID 和客户端 ACK。

### 5.14 Web 前端为什么需要网关

浏览器只支持 HTTP/WebSocket 等受限协议，不能创建任意 TCP socket。网关完成协议适配，并保持 C++ 服务端协议不变。

### 5.15 为什么不用 Protobuf

JSON 便于学习、调试和展示，当前流量规模下足够。如果压测证明序列化或带宽成为瓶颈，再切 Protobuf；不应只为技术栈更丰富而切换。

### 5.16 为什么不是微服务

当前团队和代码规模小，模块化单体更易保持一致性和调试。只有认证、关系或消息模块需要独立扩容、发布或由不同团队维护时，才值得拆分。

### 5.17 项目可以支持多少并发

**问：这个项目可以支持多少并发，是怎样测试的？**

> 我不会把架构理论值当成实测上限。当前有证据的基线是：在单机 Docker、18 CPU、7.75 GiB 内存的双 ChatServer 环境中，验证过 200 个同时在线 WebSocket 连接和 5,000 条突发消息。历史版本单节点本地直投约 11,627.91 条/秒，双节点 RabbitMQ 跨节点约 3,380.66 条/秒，该范围内 ACK 和接收数完整，没有观察到丢失、重复或单发送者乱序。但当前 RabbitMQ 已增加同步 publisher confirm，新链路尚未在相同环境重测，所以旧的跨节点吞吐只能作历史基线，不能当作当前版本 SLA。
>
> 压测用真实 WebSocket 客户端批量建连、注册和登录，然后让 100 对发送者/接收者每对突发发送 50 条消息。消息阶段单独计时，同时统计吞吐、P50/P95/P99 延迟、ACK 数、实际接收数，并用 `message_id` 检查丢失和重复、用 `client_seq` 检查单发送者顺序。还分别测单节点本地直投和双节点 RabbitMQ 路径，并做 RabbitMQ/MySQL 故障注入。

面试官继续问“上限是多少”时，应说目前只能证明“至少在已测的 200 连接和 5,000 条突发消息下正常”，尚未通过逐级加压找到饱和点。当前主要吞吐边界是同步 MySQL 连接/查询、互斥锁串行的单 Redis 连接，以及锁内同步等待的 RabbitMQ publisher confirm。

延迟数字也要说明口径：脚本将 5,000 条消息尽快突发写入，并从每条写入前计时到接收端解帧，所以 P50/P95/P99 是包含缓冲与排队的端到端延迟，不是单条消息的纯服务端执行时间。若被追问用户日常体感，应承认现有数据不足：还需补低速率稳态延迟、分档施压的延迟-吞吐曲线以及分段 Trace，才能判定日常流量下的真实瓶颈。

## 8. 不要过度表述

不要写：

- “保证消息绝不丢失”；
- “实现 Exactly Once”；
- “支持百万并发”；
- “实现分布式全局有序”；
- “生产级安全”；
- “同时基于 Redis、Kafka、RabbitMQ 实现集群通信”。

可以写：

- “通过 ACK、重试和幂等去重降低重复与丢失风险”；
- “使用 RabbitMQ direct routing 完成双节点定向投递”；
- “构建可复现的容器化全链路测试”；
- “识别现有 auto ACK、离线删除确认窗口等边界，并给出后续方案”。

能够主动讲清边界，通常比堆砌夸张指标更可信。
