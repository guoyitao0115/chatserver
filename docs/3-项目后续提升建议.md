# 文档3：项目后续提升建议

## 1. 原则

后续优化应先解决“正确性和可验证性”，再追求技术数量。当前项目用于学习和面试，最重要的是能解释为什么做、解决了什么、还缺什么。

## 2. P0：优先改进

### 2.1 RabbitMQ 可靠消费

已完成基础补强：publisher confirm、mandatory return、persistent 消息、durable 节点
队列、manual ACK/NACK 和断线重连已经实现；发布失败仍同步写离线表。

仍需继续：

1. 为反复 NACK 的消息增加有限重试次数和死信队列，避免永久热循环；
2. 加入 RabbitMQ 停止、恢复、ACK 丢失和节点重启的自动化故障测试；
3. 评估同步逐条 confirm 的吞吐，再决定批量 confirm 或异步 confirm；
4. 若目标是更强一致性，再研究 Outbox/Inbox，而不是声称 Exactly Once。

### 2.2 离线消息确认

当前登录响应带回离线消息后立即删除。服务端发送成功但客户端未处理就断线时，消息可能丢失。

建议给离线消息增加 ID，并提供 `OFFLINE_MSG_ACK`：

- 登录只查询，不删除；
- 客户端处理成功后按 ID 确认；
- 服务端收到确认后删除；
- 超期消息由定时任务清理。

### 2.3 数据库访问

当前每个操作新建 MySQL 连接，SQL 仍以转义加字符串拼接为主。

建议：

- 小型固定连接池；
- MySQL prepared statement；
- 明确事务边界，例如“建群 + 加创建者”应在同一事务；
- 为好友、群成员、离线消息补充唯一键和必要索引；
- 返回明确错误，不要只写日志。

### 2.4 在线状态单一事实来源

当前 MySQL `state` 和 Redis 路由都表达在线状态，可能短暂不一致。

建议：

- Redis TTL 作为实时在线状态的唯一事实来源；
- MySQL `state` 只作为展示缓存，或直接删除；
- 登录冲突用带会话令牌的 Redis 原子操作判断；
- 下线时只删除与当前 session/server 匹配的路由，避免旧连接误删新连接。

### 2.5 安全入口

当前适合本地演示，不适合直接暴露到公网。生产化至少需要：

- TLS/WSS；
- 登录限流、IP 限流和连接数限制；
- 随机高强度中间件密码和密钥管理；
- 登录成功后使用不可伪造的 session token；
- 昵称与消息内容长度、UTF-8 和敏感输出检查；
- 审计日志与聊天内容日志分离。

## 3. P1：完善工程质量

### 3.1 统一业务响应

添加好友、建群、加群目前没有专用响应，前端只能提示“请求已提交”。建议为每种写操作增加 ACK，包含：

- 请求 ID；
- 成功或失败；
- 可展示错误；
- 新创建资源 ID。

### 3.2 优雅停机

当前信号处理仍较简单。建议：

1. 停止接受新连接；
2. 等待正在执行的请求结束；
3. 清理当前节点的 Redis 路由；
4. 停止 RabbitMQ 消费并关闭连接；
5. 最后退出 EventLoop。

不要在异步信号处理函数中执行数据库操作。

### 3.3 可观测性

增加但不要过量：

- 登录成功/失败数；
- 当前连接数；
- 本地、RabbitMQ、离线三种投递计数；
- ACK 延迟和重试次数；
- Redis/MQ/DB 错误数；
- 离线积压和死信数量。

可先输出 Prometheus 文本指标，再考虑 tracing。

### 3.4 测试

继续增加：

- 服务端 handler 级测试，需要把数据库和消息总线抽成接口；
- 帧头 1～3 字节、粘包、多帧、超大帧、非法 JSON 的网络测试；
- Redis 故障时本地去重回退测试；
- RabbitMQ 发布失败后的离线兜底测试；
- 断线、重复登录、旧连接误注销测试；
- ThreadSanitizer、AddressSanitizer；
- 固定机器上的基准测试。

## 4. P2：有数据后再做

### 4.1 性能

先压测定位瓶颈，再选择：

- 批量或异步数据库写入；
- Redis 连接池或每 IO 线程一连接；
- RabbitMQ 发布连接池；
- JSON 换 Protobuf；
- 群聊扇出异步化；
- 热点群分片。

当前已经有单机 Docker 环境下 200 连接、5,000 条消息的基线数据，详见测试报告；
仍应先根据指标定位瓶颈再实施这些优化，不能把单机结果外推为大规模生产能力。

### 4.2 架构拆分

只有出现独立扩容、独立发布或团队边界时，再拆认证、关系、消息服务。当前模块化单体更适合学习、调试和面试展示。

## 5. 建议删除或避免的冗余

- 不同时维护 Redis Pub/Sub、Kafka、RabbitMQ 三套跨节点方案；当前只保留 RabbitMQ；
- 不为展示技术栈再引入 Elasticsearch、Kubernetes、微服务注册中心；
- 不追求所有用户的“全局消息顺序”；聊天通常只需会话内合理顺序；
- 不把 WebSocket、HTML 静态服务硬塞进 C++ 聊天核心；独立适配层更清楚；
- 不把 Snowflake 本身当亮点，重点应是“消息 ID 支撑 ACK、重试和幂等”；
- 不声称高并发、零丢失、强一致，除非有测试和设计证明。

## 6. 推荐迭代路线

| 阶段 | 内容 | 验收标准 |
|---|---|---|
| 1 | 业务响应、prepared statement、事务 | 错误可回传，核心写操作原子化 |
| 2 | 离线消息 ACK、MQ 死信/批量 confirm | 故障注入后可解释消息状态 |
| 3 | 在线状态统一、会话令牌、限流 | 旧连接不能覆盖或删除新会话 |
| 4 | 指标、故障测试、sanitizer | 故障测试和 ASan/UBSan 已完成；继续补 ThreadSanitizer 与监控指标 |
| 5 | 压测与针对性优化 | 已有可复现基线；继续扩展连接规模、长稳测试和瓶颈优化 |

## 7. 简历前最值得完成的三项

如果时间有限，优先：

1. 离线消息 ID + 客户端确认删除；
2. RabbitMQ 有限重试 + 死信队列，并补断线恢复自动化测试；
3. 基于现有可复现压测报告重新测试同步 confirm 后的吞吐和长稳曲线。

这三项比继续增加新中间件更有面试价值。
