### 文件与行号

- `src/client/main.cpp:67` `recvFrame(...)`
- `include/server/chatserver.hpp:36` `onMessage(...)`

### 核心代码

```cpp
// src/client/main.cpp:36
static int sendFrame(int fd, const string &payload)
{
    uint32_t netLen = htonl(static_cast<uint32_t>(payload.size()));
    string frame;
    frame.reserve(4 + payload.size());
    frame.append(reinterpret_cast<const char *>(&netLen), 4); // 先写4字节长度头
    frame.append(payload);                                     // 再写JSON内容
    // ... 循环send直到全部发出
}
```

### 解释
- **问题**：TCP 是流式协议，一个 `send` 对应多少个 `recv` 是不确定的，直接读 JSON 很容易读到"半截"或"多条粘在一起"。
- **解法**：在发送时在 payload 前面加 `4字节 Big-Endian 长度头`，接收时先读4字节拿到长度，再精确读那么多字节，保证每次 `recvFrame` 拿到的一定是完整的一条 JSON。
- **服务端**：`FrameCodec` 做同样的解帧，`onMessage` 只负责喂数据给 `FrameCodec`，`onFrameMessage` 只处理完整业务帧，两层分离。

### 核心代码

```cpp
// src/server/chatservice.cpp:116
void ChatService::sendAck(const TcpConnectionPtr &conn,
                          const string &msgId,
                          int ackState)
{
    if (!conn || !conn->connected() || msgId.empty())
        return;  // 无 message_id 的旧客户端不回ACK，保持兼容

    json ack;
    ack["msgid"]      = MSG_ACK;   // 消息类型：服务端ACK
    ack["message_id"] = msgId;     // 回填原消息的ID，客户端据此定位pending
    ack["ack_state"]  = ackState;  // 0=成功 1=去重跳过 2=失败
    conn->send(FrameCodec::encode(ack.dump()));
}
```

### 解释
- **问题**：发送方"发出去就算完"，服务端宕机、网络中断都不知道。
- **解法**：服务端处理完每条聊天消息后，立即向发送方回一个 `MSG_ACK`，里面带上 `message_id` 和 `ack_state`。
- `ACK_OK`：消息正常处理并投递。
- `ACK_DEDUP`：消息是重复的，已跳过，告知客户端停止重试。
- `ACK_FAIL`：处理失败，客户端可选择重试。
- ACK 走帧编码发出，避免客户端收包错位。

```cpp
// src/client/main.cpp:210
static void addPending(const string &msgId, const string &payload)
{
    lock_guard<mutex> lock(g_pendingMutex);
    g_pendingMap[msgId]   = payload;                          // 记录原始消息
    g_pendingTime[msgId]  = chrono::steady_clock::now();     // 记录发送时间
    g_pendingRetry[msgId] = 0;                               // 初始重试次数=0
}

// src/client/main.cpp:228（retryTaskHandler 核心逻辑）
// 每秒扫描一次 pending 列表
// elapsed >= RETRY_TIMEOUT_SEC(5s)：触发重试
// cnt < MAX_RETRY_COUNT(3)：重发并递增计数
// cnt >= MAX_RETRY_COUNT：放弃，打印告警，从 pending 移除
```

### 解释
- **问题**：消息发出后记录在 pending，但没有后台线程去检查是否超时、是否需要重发。
- **解法**：
  1. `addPending` 在发送时记录消息、时间、重试次数。
  2. 后台 `retryTaskHandler` 每秒扫描，超过 5 秒未收到 ACK 则重发。
  3. 重试次数超过 3 次则放弃并打印告警，防止无限重试。
  4. 收到 `MSG_ACK` 时调用 `removePending` 将消息从 pending 中移除。
- **并发安全**：`addPending/removePending/retryTaskHandler` 均用 `g_pendingMutex` 保护。

```cpp
// 返回值：1=首次写入(非重复)  0=已存在(重复)  -1=执行失败
int Redis::markMessageIfFirst(const string &key, int ttlSeconds)
{
    redisReply *reply = (redisReply *)redisCommand(
        _publish_context,
        "SET %s 1 EX %d NX",  // NX=仅key不存在时写入，EX=TTL自动过期
        key.c_str(),
        ttlSeconds);
    // reply->type==REDIS_REPLY_STATUS && reply->str=="OK" -> 首次写入
    // reply->type==REDIS_REPLY_NIL -> 已存在（重复）
}

// src/server/chatservice.cpp:85
bool ChatService::isDuplicateWithFallback(const string &msgId)
{
    int ret = _redis.markMessageIfFirst(REDIS_DEDUP_KEY_PREFIX + msgId, 120);
    if (ret == 1) return false; // 首次出现
    if (ret == 0) return true;  // 重复
    // Redis异常时回退本地LRU+TTL去重（msgdedup.hpp）
    return _dedup.isDuplicate(msgId);
}
```

### 解释
- **问题**：原来去重用本地内存，多个服务实例各自维护，A实例已去重的消息B实例不知道，重启后去重状态全失。
- **解法**：改为 Redis 原子命令 `SET key 1 EX ttl NX`：
  - `NX`（Not Exist）：只在 key 不存在时写入 -> 天然幂等，首次返回 OK，重复返回 NIL。
  - `EX ttl`：自动过期，无需手动清理。
  - 多实例共享同一 Redis，去重状态跨实例一致。
- **兜底**：Redis 不可用时（返回 -1），自动降级到本地 `MsgDedup`（LRU+TTL），保证功能不中断。

```cpp
// src/client/main.cpp:165 - 发送端序号：按目标维度独立递增
static mutex g_clientSeqMutex;
static unordered_map<int, uint64_t> g_peerClientSeq;   // key=toid
static unordered_map<int, uint64_t> g_groupClientSeq;  // key=groupid

static uint64_t nextClientSeqForPeer(int toid)
{
    lock_guard<mutex> lock(g_clientSeqMutex);
    uint64_t &seq = g_peerClientSeq[toid];
    seq += 1;   // 只对该接收者的序号递增，不影响其他接收者
    return seq;
}

// src/client/main.cpp:770 - 单聊发送时附加序号
js["client_seq"] = nextClientSeqForPeer(friendid);  // 按 toid 维度

// src/client/main.cpp:824 - 群聊发送时附加序号
js["client_seq"] = nextClientSeqForGroup(groupid);  // 按 groupid 维度

// src/client/main.cpp:360 - 接收端按序号排序显示
static void printOrderedIncoming(const json &js)
{
    string key = buildSessionKey(js);  // 单聊:"u:userid" 群聊:"g:groupid:u:userid"
    uint64_t seq = js["client_seq"].get<uint64_t>();
    uint64_t &last = g_lastShownSeq[key];
    if (seq <= last) return;  // 重复或过期消息直接丢弃
    g_orderBuffer[key][seq] = formatIncomingLine(js);
    // 从 last+1 开始连续冲刷 buffer
    auto &buf = g_orderBuffer[key];
    while (!buf.empty() && buf.begin()->first == last + 1)
    {
        cout << buf.begin()->second << endl;
        last = buf.begin()->first;
        buf.erase(buf.begin());
    }
}
```

### 解释
- **问题**：若序号全局递增，A 给 B 发 seq=1，A 给 C 发 seq=2，B 的接收方看到 seq=1 后等待 seq=2，但 seq=2 是给 C 的，永远不会到 B，导致 B 后续消息全部卡在 buffer。
- **解法**：按目标维度维护独立序号：
  - 单聊：每个 `toid` 一条独立递增序列，A 给 B 和 A 给 C 完全独立。
  - 群聊：每个 `groupid` 一条独立递增序列，群 G1 和群 G2 不相互干扰。
- **接收端**：`buildSessionKey` 按同样的维度构建 session key，保证同一发送者在同一会话内的消息按序排列。
- **并发安全**：两个线程（主线程发送、重试线程重发）都会调用 `nextClientSeqForPeer/Group`，用 `g_clientSeqMutex` 保护。

```cpp
// src/client/main.cpp:88
class SnowflakeIdGenerator
{
public:
    explicit SnowflakeIdGenerator(uint16_t workerId = 1)
        : _workerId(workerId & WORKER_ID_MASK) {}

    void setWorkerId(uint16_t workerId) { ... }

    uint64_t nextId()
    {
        lock_guard<mutex> lock(_mtx);
        uint64_t ts = nowMs();
        // 时钟回拨保护：回拨窗口内强制使用 lastTs，保证单调不倒退
        if (ts < _lastTs) ts = _lastTs;
        if (ts == _lastTs) {
            _seq = (_seq + 1) & SEQ_MASK;  // 同毫秒内序号递增
            if (_seq == 0) ts = waitNextMs(_lastTs); // 序号溢出则等下一毫秒
        } else {
            _seq = 0;
        }
        _lastTs = ts;
        // ID 格式：[41位时间戳][10位workerId][12位序号]
        return ((ts - EPOCH_MS) << TIMESTAMP_SHIFT)
             | (_workerId << WORKER_ID_SHIFT)
             | _seq;
    }
private:
    static constexpr uint64_t EPOCH_MS = 1704067200000ULL; // 2024-01-01
    mutex _mtx; uint16_t _workerId; uint64_t _lastTs = 0, _seq = 0;
};

// src/client/main.cpp:520 - 登录成功后设置 workerId
g_snowflake.setWorkerId(static_cast<uint16_t>(g_myUserId & 0x3FF));
// 用 userId 低10位作 workerId，保证同一用户不同登录实例ID不冲突

// src/client/main.cpp:189
static string generateMsgId() { return to_string(g_snowflake.nextId()); }
```

### 解释
- **问题**：原 `message_id` 用"用户ID+时间+本地序号"字符串拼接，在多实例或时钟误差下存在碰撞风险。
- **解法**：改用 Snowflake 64位分布式ID：
  - **41位时间戳**：毫秒级，可用约69年。
  - **10位 workerId**：用 `userId & 0x3FF`，同一用户的不同实例不冲突。
  - **12位序号**：同毫秒内最多4096条消息不冲突。
- **线程安全**：`nextId()` 内持锁，主线程与重试线程并发调用安全。
- **时钟回拨保护**：若 `ts < lastTs`，强制使用 `lastTs`，保证ID单调递增不回退。
- **兼容性**：服务端字段名仍是 `message_id`，ACK/重试/去重链路完全不变。

```cpp
// src/client/main.cpp:288 - 客户端心跳发送线程
static void heartbeatTaskHandler(int clientfd)
{
    while (true)
    {
        this_thread::sleep_for(chrono::seconds(HEARTBEAT_INTERVAL_SEC)); // 每10秒
        if (g_myUserId <= 0) continue; // 未登录不发

        if (!g_heartbeatAcked.load())
        {
            // 上一轮心跳未被ACK，说明连接可能已失效
            cerr << "[heartbeat] warning: last heartbeat not acked, connection may be lost" << endl;
        }

        json hb;
        hb["msgid"] = HEARTBEAT_MSG;
        hb["id"] = g_myUserId;
        hb["ts"] = chrono::duration_cast<chrono::milliseconds>(
            chrono::system_clock::now().time_since_epoch()).count();
        g_heartbeatAcked = false;  // 标记等待ACK
        sendFrame(clientfd, hb.dump());
    }
}

// src/server/chatservice.cpp:588 - 服务端立即回应
void ChatService::heartbeat(const TcpConnectionPtr &conn, json &js, Timestamp time)
{
    json ack;
    ack["msgid"] = HEARTBEAT_MSG_ACK;
    if (js.contains("ts")) ack["echo_ts"] = js["ts"]; // 回显时间戳便于延迟计算
    conn->send(FrameCodec::encode(ack.dump()));
}

// src/client/main.cpp:638 - 收到ACK时置标志
g_heartbeatAcked = true;
```

### 解释
- **问题**：TCP 长连接在 NAT 超时、半开连接等场景下，连接表面存在但实际不通，应用层长时间感知不到。
- **解法**：客户端每 10 秒发一次 `HEARTBEAT_MSG`，服务端立即回 `HEARTBEAT_MSG_ACK`。
- `g_heartbeatAcked`（`atomic_bool`）：发送前置 false，收到 ACK 后置 true。
- 下一轮发送前检查：若仍是 false，说明上一轮 ACK 未到，打印告警。
- **不直接断线**：避免网络抖动导致误断，由用户/更高层逻辑决定是否重连。
- **服务端**：`HEARTBEAT_MSG` 注册进 `_msgHandlerMap`（第44行），像普通消息一样分发处理。

```cpp
    _redis.setUserServer(js["id"].get<int>(), _serverId, 120);
}

// src/server/chatservice.cpp:635 - direct 消费后本地投递；连接已不存在则离线兜底
void ChatService::handleRabbitMqBusMessage(int userid, string msg)
{
    {
        lock_guard<mutex> lock(_connMutex);
        auto it = _userConnMap.find(userid);
        if (it != _userConnMap.end())
        {
            it->second->send(FrameCodec::encode(msg));
            LOG_INFO << "[rabbitmqMsg] userid=" << userid << " route=local";
            return;
        }
    }

    bool insertOk = _offlineMsgModel.insert(userid, msg);
    if (!insertOk)
        LOG_ERROR << "[rabbitmqMsg] userid=" << userid
                  << " route=offline_fallback insert_failed";
}
```

### 解释
- **问题**：上一版 RabbitMQ 采用 `fanout` 广播，每条跨节点消息会被所有节点消费一次，节点数上来后无效消费线性增长。
- **解法**：升级为 **direct 精确路由**：
  - 每个实例启动时使用自身 `_serverId` 作为 queue binding key。
  - 登录成功后，将 `userId -> serverId` 写入 Redis（带 TTL）。
  - 发送消息时先查目标 `serverId`，再调用 `publish(toServerId, ...)` 定向投递。
- **可靠性兜底**：
  - 路由缺失或 RabbitMQ 发布失败，统一降级写离线库（`offline_fallback`）。
  - 消费端收到消息时若目标连接刚断开，不再忽略，改为写离线库兜底。
- **路由保活**：心跳处理里刷新 `userId -> serverId` TTL，避免长会话下路由键过期。
- **下线清理**：正常注销与异常断线都会删除在线路由，避免脏路由长期驻留。
- **收益**：跨节点消息从“广播给 N 个节点”降为“投递给 1 个节点”，在多节点部署下显著减少网络/CPU 消耗。

```cpp
// src/server/security/password_hasher.cpp:46
string PasswordHasher::hashBcrypt(const string &plain, int rounds)
{
    string salt = generateBcryptSalt(rounds);
    // salt 格式：$2b$12$<22位随机字符>
    // 每次注册生成不同随机盐，相同密码哈希值也不同，防彩虹表
    struct crypt_data data;
    data.initialized = 0;
    char *out = crypt_r(plain.c_str(), salt.c_str(), &data);
    // crypt_r 是线程安全版本，data 由调用方分配，避免全局状态竞争
    return out ? string(out) : "";
}

// src/server/security/password_hasher.cpp:62
bool PasswordHasher::verifyBcrypt(const string &plain, const string &storedHash)
{
    // 将 storedHash 作为 salt 传入，crypt_r 自动提取算法/cost/salt 并重新计算
    // 结果与 storedHash 相同则密码正确
    struct crypt_data data;
    data.initialized = 0;
    char *out = crypt_r(plain.c_str(), storedHash.c_str(), &data);
    return out && (storedHash == string(out));
}

// src/server/chatservice.cpp:210 - 登录时兼容历史明文账号
bool authOk = false;
if (isBcryptHash(storedPwd))
    authOk = PasswordHasher::verifyBcrypt(pwd, storedPwd);  // 新账号
else
    authOk = (storedPwd == pwd);                             // 历史明文兼容

// src/server/chatservice.cpp:249 - 首次明文登录成功后自动升级
if (needUpgradeToBcrypt)
{
    string newHash = PasswordHasher::hashBcrypt(pwd, 12);
    if (!newHash.empty()) _userModel.updatePassword(id, newHash);
    // 下次登录即走 bcrypt 校验路径，平滑迁移无感知
}
```

### 解释
- **问题**：用户密码明文存入数据库，数据库泄露即等于账号全部裸露。
- **解法**：
  - 注册时用 `hashBcrypt(pwd, 12)` 生成含随机盐的 bcrypt 哈希存入库。
  - 登录时用 `verifyBcrypt` 校验，无需知道原始盐（从哈希字符串中自动提取）。
  - `isBcryptHash` 检查 `$2a$/2b$/2y$` 前缀：历史明文账号仍走明文比对，登录成功后自动回写 bcrypt 哈希完成平滑迁移。
  - `crypt_r`（非 `crypt`）：线程安全，`data` 栈上分配，无全局状态竞争。
  - `rounds=12`：bcrypt cost 参数，计算时间约 100-300ms，有效对抗暴力破解。
